# SADD behavior benchmark and demonstration protocol

## What the shipped numbers mean

The default application snapshot is **synthetic_lab**, not CERT and not a live
enterprise deployment. `dataset_generated=true` and
`label_provenance=explicit_synthetic_scenario_schedule_v1` travel with the result.
The fixture models 40 fictional users in five roles for 84 completed calendar
days, 2026-08-08 through 2026-10-30. It contains ordinary variability, a busy
Finance user, normal night workers, a benign workstation replacement, periodic
bulk copying, and predeclared malicious-scenario interventions. No measurements
are added manually after fitting. Labels are never model features and never
select which history is admitted to the model.

The default snapshot is generated by:

```python
from sadd.behavior import build_demo_snapshot
snapshot = build_demo_snapshot(seed=42)
```

`subjects` and `records` contain the latest **completed** day for all 40 users;
`history` contains compact scores for the chronological test interval. The live
gateway consumes this dated background context. It does not feed a partial day
into a full-day model, impersonate a CERT user, or silently update the historical
ML result after each prompt. Actual subsequent events belong in the live event
timeline and must retain their separate provenance.

## Behavior model

Scoring unit: one completed user-day of removable-media copying. A 28-observation
past-only history is maintained per user; scoring starts after 14 prior observed
days. All users for a given day are scored before any same-day history is added.
Peer adjustment requires at least five other adequately observed users with the
same recorded role. Roles in the lab are generated metadata, not inferred human
attributes. Missing or thin peer groups explicitly fall back to personal history.

Three rules are independently visible:

1. Copy volume: severity begins above the larger of the personal and valid peer
   median-plus-three-robust-scale thresholds, reaches one at the corresponding
   nine-scale reference, and is clipped to [0,1]. Robust scale is the larger of
   1.4826 MAD, one, and the square root of the median count. A stable busy worker
   is therefore compared with their own history as well as available peers.
2. Unusual-hour copying: the daily fraction of copies outside reference hours is
   compared with that user's previous daily fractions. Median/MAD with a 0.05
   scale floor and at least three such copies prevents a single tiny denominator
   from generating the maximum severity. A regular night worker can be normal.
3. Novel workstation: a workstation unseen in the user's past is weighted by
   copying context and whether peers have previously used it. At least five
   copies and the personal-history guard are required. Novelty is an
   investigation lead, not proof of unauthorized access.

`R` is the maximum of those three severities; correlated signals are not added
as though independent evidence. A pooled Isolation Forest uses the seven named
features in `FEATURE_NAMES`: log copy count, personal and peer volume deviation,
after-hours fraction/deviation, novel-workstation fraction, workstation count.
It has 160 trees, fixed seed, `contamination="auto"`, and no label input. The
raw anomaly score is negative `score_samples`, so higher means more unusual.

The validation q95/q99 map the raw anomaly score to the displayed tail priority:

`A = clip((raw_anomaly - q95) / (q99 - q95), 0, 1)`.

At least 200 finite validation samples and distinct quantiles are required.
Otherwise the ML tail is marked uncalibrated and contributes zero; this is not
an assertion that the user is safe. Raw anomaly and rule evidence remain visible.

`B = round(100 * (0.6 R + 0.4 A))` is the displayed behavior priority. The weights,
floors, and thresholds are predeclared engineering parameters, not learned
probabilities. Unrounded combined priority is used for evaluation to avoid
display-rounding ties. Neither B nor A estimates malicious intent.

## Chronology, calibration, and held-out evaluation

- Warm-up: the first 14 observed days per user are excluded from scored rows.
- Train: through 2026-09-18; 1,120 scored user-days.
- Validation: 2026-09-19 through 2026-10-09; 840 user-days.
- Final test: 2026-10-10 through 2026-10-30; 840 user-days.

No random split is used. All historical features are calculated using preceding
observations only. Prior anomalous observations enter subsequent history because
real systems do not know future ground truth; labels never filter those updates.
The model is fitted once on training features. The score calibration and alert
operating points use validation scores only. Test labels are used only after
predictions have been made, for measurement. The test data must never select
weights, features, thresholds, or demo interventions. Any future revision must
create a new protocol/model version and a new untouched final holdout.

Rules, Isolation Forest, and combined priority are compared on the same test
user-days. Each uses a validation-selected threshold allowing at most one
behavior alert per 100 validation user-days by default. This is an analyst
candidate budget, **not** a cap that disables content protection. Threshold ties
are resolved conservatively: if all tied scores would exceed the budget, that
tied block is excluded. Zero alerts are possible and explicitly reported. No
labels are used to force a desired precision or candidate count.

Measurements include user-day TP/FP/FN/TN, precision/recall/F1, average precision
(scikit-learn AP, not a differently integrated PR area), ROC AUC, alerts per 100
user-days, and false alerts per normal user-days and calendar day. The number of
positive examples and cohort size accompany every result. Rules and ML are
reported separately, even when the combination fails to improve them.

An actor is a detected actor only if an alert occurs on that actor's labeled
malicious day. An earlier alert on a benign day never counts as a true detection.
Episode recall requires an alert inside the supplied labeled episode. Actor and
episode recall are supplemental; they do not replace user-day confusion counts.
No actor-level F1 is manufactured from a mixture of incompatible time units.

## CERT r4.2 intake

The repository supplies a **local-file importer** and a separately identified
completed CERT benchmark artifact. The large source archive is acquired locally;
it is not required to run the synthetic lab demonstration:

```bash
python scripts/cert_ingest.py --input /absolute/path/file.csv --output /absolute/path/cert_user_days.jsonl
```

The importer requires r4.2 `id,date,user,pc,filename,content` columns, rejects
duplicate IDs and malformed rows, and rejects later-release activity schemas.
It rejects an unterminated final record and verifies source length/mtime remain
stable through hashing and parsing. For the complete official r4.2 file.csv,
pass `--expected-size 193055265`, using the verified archive member header.
Compare actual extracted length with that header before evaluating; a manifest
that merely repeats an expected length is not evidence the copy completed.
It uses disk-backed SQLite aggregation rather than retaining the whole CSV in
memory. Local SHA256, source size, schema, rows, timeframe, output hash and the
interpretation of reference hours are preserved in a metadata sidecar.

**r4.2 file.csv records copies to removable media.** It must not be described as
all file reads, all document access, or AI traffic. Content is discarded and
filenames are not emitted. A SHA256 computed locally establishes reproducibility;
it does not authenticate an unknown extract against the publisher. A caller can
provide an independently known CSV checksum with `--expected-sha256`.

Output users/hosts are namespaced `cert-r4.2:`. Without `--answers-archive`, labels
remain null and benchmark execution is rejected. Null never means benign.
With the official archive, the importer reads the `insiders.csv` master and
incident observables. The actual r4.2 answers contain only ten `file` observable
IDs, all from scenario 3; scenarios 1 and 2 provide other-channel observables.
Consequently, exact-file-ID-only labels would omit most incidents. Before any
CERT scoring, the protocol therefore defines the primary target as an
**incident-associated copy user-day**: an actual copy by the master's declared
actor occurs inside that incident's inclusive start/end timestamp interval.
This coarse contextual label does not prove every copy on that day malicious.
Exact file IDs for the declared actor remain supplementary stronger evidence.
Other actors' contextual observables do not relabel their normal days. Earlier
normal days of a known insider are not automatically positives. Label and
archive hashes are retained, with interval definitions, exact matches, unmatched
IDs, and excluded-context counts. This target differs from published all-channel
benchmarks and must be named explicitly when reporting precision or recall.

`--ldap-dir` enables as-of monthly `YYYY-MM.csv` snapshots requiring `user_id`
and `role`. A future month's role never annotates an earlier event. Missing
roles remain Unknown. No artificial role assignments are supplied. Imported
active days are preserved; inactive days are not silently invented. An
evaluation must document its active-day/zero-day population and time interval.

After the publisher archive is acquired and file.csv/LDAP are extracted, the
optional benchmark is invoked as follows (replace paths with actual locations):

```bash
python scripts/cert_ingest.py --input /absolute/path/r4.2/file.csv --output /absolute/path/user_days.jsonl --answers-archive /absolute/path/answers.tar.bz2 --ldap-dir /absolute/path/r4.2/LDAP --benchmark-output /absolute/path/cert_benchmark.json --max-users 0 --train-end 2010-06-30 --validation-end 2010-09-30
```

The first valid official-source run selected the full cohort with `--max-users 0`.
The CLI also supports a 200-user cohort selected by the lowest SHA256 hashes of
source subject IDs before labels or scores are examined; any reduced cohort
must be explicitly identified and cannot replace a poor full-cohort result.
The eligible roster is the union of file-source and dated LDAP identities, so
missing file activity does not silently remove a rostered person. All selected
master incidents that overlap test remain in actor/episode recall denominators,
including incidents with no observable copy and those excluded by history
requirements. Coverage reports both conditions explicitly. Source-conditional
recall is retained separately and never substituted for coverage-adjusted recall.
The explicit calendar cutoffs are fixed before evaluating results. Feature
warm-up can further reduce eligible rows; report the measured counts. This
benchmark uses a separately fitted `cert_daily_v1` model and calibration,
`cert_synthetic` provenance, source-local timestamps with unspecified timezone,
and the stated active-copy-day population. It is not directly comparable with
papers that aggregate all channels or insert inactive calendar days.

The benchmark writes a separate compressed `*.model.joblib` artifact containing
the fitted forest, feature order, calibration, operating points, seed, cutoffs,
profile and scikit-learn version. Its local hash is included in the results.
This is a trusted local pickle-based artifact, not an upload/import feature;
never load arbitrary downloaded model files. Reconstructing past-only features
also requires the versioned source history and feature code, not just the forest.

CERT is itself synthetic. It is a published research dataset; it is not real
employee telemetry. Keep `cert_synthetic` benchmark output separate from
`synthetic_lab` live tests, with separate fitted models and calibrations. Do not
join unrelated CERT identities to lab AI requests and present the result as
observed evidence. A daily removable-media model cannot be assumed to transfer
to prompt-level behavior without a separately evaluated feature contract.

## Completed CERT run: a measured failure, not an efficacy claim

The complete source was verified as 193,055,265 bytes with SHA256
`637281bd6d8947b2cccf90bca7096e8cfad711eab1e425c61f886b0e4edfda7f`.
The hash was checked again after evaluation. Strict parsing found 445,581 events
from 2010-01-02 07:23:14 through 2011-05-16 23:22:34, producing 45,907 active
copy user-days for 264 copy-active identities. All 1,000 dated LDAP roster
identities were eligible for coverage accounting; this does not mean all 1,000
had modeled activity. All ten supplementary exact file-event IDs were matched.
The primary interval-based target marks 860 source user-days positive.

The frozen chronological protocol produced 14,963 training, 8,861 validation,
and 18,812 test user-days; 3,271 initial-history days were excluded. Test spans
2010-10-01 through 2011-05-16 and contains 476 contextual positive days and
18,336 negative days. These counts describe this file-only active-day protocol,
not the full all-channel CERT population used by other papers.

| Detector | Test TP | Test FP | Test FN | Test TN | Average precision | ROC AUC |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Rules | 0 | 0 | 476 | 18,336 | 0.025719 | 0.500274 |
| Isolation Forest | 0 | 120 | 476 | 18,216 | 0.022285 | 0.448515 |
| Combined | 0 | 100 | 476 | 18,236 | 0.025451 | 0.498099 |

Every operating threshold was selected from validation scores only, with a
maximum budget of one alert per 100 validation user-days. At the rule boundary,
the tied highest-severity group exceeded that budget; the predeclared
conservative tie policy therefore selected no rule alerts. This is explicitly
reported rather than changing the policy after observing test outcomes.

Coverage-adjusted actor and episode recall are **0/40** for all three detectors.
Of the forty master incidents overlapping the test interval, eight have no
observed copy inside their interval, ten have observed copies but no scoreable
positive day after the fourteen-observation history requirement, and twenty-two
have scoreable positive days. The first eighteen remain misses in the primary
denominator. Of the 476 scored positive days, 471 belong to scenario 2 and five
to scenario 3; these are contextual interval labels, not proof that each file
copy is malicious. The file-only features do not represent the other channels
that define many incidents. This is a plausible limitation, not proof of the
sole cause of the measured failure.

The result demonstrates a functioning reproducible evaluation pipeline and a
failure of this frozen detector configuration on this target. It **does not**
demonstrate useful CERT detection performance. The successful controlled lab
scenarios remain functional tests. No feature, weight, cutoff, history policy,
cohort, or threshold was changed to improve this test result. A future model
revision needs an explicitly versioned protocol and a new untouched holdout;
this run cannot become its independent validation set.

Artifacts: `artifacts/cert_benchmark.json`, `artifacts/cert_benchmark.model.joblib`,
`artifacts/cert_source_metadata.json`, and
`artifacts/cert_benchmark_run_summary.json`. Import plus model/evaluation took
29.55 seconds with approximately 409 MiB peak resident memory in this execution
environment; those are measured local resource costs, not deployment SLAs.

## Acceptance checks

Run `python -m unittest discover -s tests -p 'test_behavior.py' -v`.
The suite checks completed-day provenance, the generated demo contrast, benign
busy/night context, chronological splits, label-independent model/thresholds,
future and same-day peer leakage, thin peer groups, tied calibration/budgets,
actor-window semantics, and the local CSV import contract. High results on this
controlled fixture are functional evidence only; they do not establish external
validity, resistance to adaptive attackers, or production false-positive rates.
