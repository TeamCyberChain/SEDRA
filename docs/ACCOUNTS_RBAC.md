# Settings and local account RBAC

Settings opens as a same-page flyout extending from the lower-left sidebar button. The workspace remains visible, with no blurred backdrop or new browser tab. Profile, Appearance and Audit Logs are inside it. Users expands into User Creation, User Management and Roles. Desktop docking is computed from the trigger; narrow screens retain an in-viewport panel. Dark mode uses graphite surfaces with restrained teal action accents across the shared web surfaces.

The first administrator is initialized explicitly through the local Profile form, requiring a 12–256 character password and a declared administrator role. No default credential is embedded. Bootstrap atomically refuses a second initialization, invalidates all existing demo sessions and permanently closes demo identity switching while any account exists. Subsequent visits require local sign-in. Account records/roles survive restart and activity reset; cookies/sessions are process-local and expire after eight hours. The UI never receives password hashes/salts. Passwords use independent random 128-bit salts and PBKDF2-HMAC-SHA256 (600,000 iterations). Login errors are generic; five attempts per username and thirty total per rolling minute are enforced using persisted metadata. CSRF, same-origin and loopback checks apply to account operations.

| Access profile | Capabilities |
| --- | --- |
| Administrator | Security review, audit access, integrations and user/role management |
| Analyst | Existing security review, audit, governed labels, endpoint controls and integrations; no account management |
| User | Governed AI/transfer actions and own bound UEBA subject; no audit/account administration |

Custom roles inherit one fixed operational profile. On Analyst-based custom roles, Administrators can additionally grant accounts.read, accounts.create, accounts.update and accounts.reset_password. Any action permission requires accounts.read. Built-in roles remain immutable. Role definitions and delegation are Administrator-only; existing custom role names and account permissions can be edited, while their operational profile stays fixed. This is a focused account-administration permission editor, not a per-action editor for every security-console operation. Accounts with a User profile require an existing UEBA subject binding; multiple accounts may share a binding and therefore share its behavior context. Administrative accounts have no employee transfer identity. Machine keys remain separately scoped service identities; disabling an account does not implicitly revoke independent integration credentials.

Administrators can create accounts/roles, update role/binding, disable/re-enable accounts and reset account passwords. Explicitly delegated operators can view the directory and perform only their granted account actions on nonprivileged accounts; they cannot modify themselves, Administrators, delegated operators or assign privileged roles. The User Management UI hides unavailable actions; the same restrictions are independently enforced by the API. Account activity and role permissions are re-read on every HTTP request, so disabled accounts lose session access immediately on the next request. A transaction prevents disabling/demoting the last active Administrator. Built-in profiles are immutable; custom role names must be unique. Password reset uses a fresh salt and increments a durable authentication version, invalidating every existing session on its next request. Disable/re-enable also advances that version, so re-enabling an account cannot resurrect an old cookie. Resets do not automatically enable disabled accounts or revoke independent machine keys. Password values never enter response bodies or audit metadata. There is no self-service recovery, temporary-password expiry, forced first-login password change, MFA, account hard-delete or multi-tenant account store. Current local account mode and the existing optional OIDC mode are mutually exclusive at startup; do not enable both. For external organizational exposure, TLS ingress and reviewed identity provisioning are required; this server continues to bind to loopback only.

Routes: GET `/api/account/context` provides the current session's setup/sign-in context and CSRF value; POST `/api/account/bootstrap`, POST `/api/account/login`; GET `/api/accounts`, POST `/api/accounts/users`, POST `/api/accounts/roles`, POST `/api/accounts/password` are protected by the current server-derived account profile. Supplying role or actor fields to ordinary transfer/session requests cannot grant management access.

Tests use isolated temporary stores and fictional passwords. Runtime accounts databases, credential files and their backups must remain outside Git. Account changes record metadata-only audit events. Stored hashes protect passwords from direct disclosure, but SQLite and local files are not immutable against an OS administrator.

The schema migration adds default-empty delegated permissions and authentication version zero without rewriting existing usernames, password hashes, bindings or role assignments. Regression tests cover a legacy database migration, delegated privilege escalation denial, immediate permission revocation, password reset/CSRF/redaction and disable/re-enable session revocation. Password resets are tested with fictional accounts in temporary loopback stores; real user credentials are not changed by the test suite.

A password reset concurrent with sign-in cannot upgrade a stale password verification into the new authentication version: the verified account version and returned claims must agree, and the HTTP session keeps that exact version. A controlled race test exercises this boundary.
